# Glossary

Terms used across MediFlow's documentation: plain English first, precisely second. The
precise column describes how the term is actually used in this codebase; the long-form
version of the Medicare material is [docs/domain.md](domain.md).

## Domain terms (the Medicare side)

| Term | In plain English | Precisely |
|---|---|---|
| Medicare Part A / Part B | Medicare's two halves: Part A pays for hospital stays, Part B for doctor and outpatient visits. The dates a member's coverage under each began matter, because enrolling in a plan keys off them. | Entitlement dates recorded on `Member` (`PartAEffective`, `PartBEffective`). Part B entitlement is the prerequisite for MA and PDP enrollment; a member without it, or whose Part B starts after the requested coverage date, cannot enroll (`PartBNotEffective`). |
| MA vs PDP | The two plan products a carrier offers. Medicare Advantage (MA) replaces Original Medicare with one private plan that covers medical care and carries the payment rules (deductible, coinsurance, out-of-pocket cap). A Prescription Drug Plan (PDP) is standalone drug coverage that can sit alongside an MA plan. | `PlanType.MedicareAdvantage` (Part C) carries the benefit design the engine adjudicates; `PlanType.PrescriptionDrug` (Part D) may coexist with an MA plan. A member may hold one active enrollment per plan type; the dual-coverage block fires per type. |
| Beneficiary (member) | The person covered by Medicare and by a plan. This repo says "member" for short. | The `Member` entity: demographics, state, Part A/B entitlement dates, identified by an MBI. |
| Carrier / provider | The two organizations on either side of a claim. The carrier (the insurer) offers the plan; the provider (a clinician or facility) treated the member and bills for it. | `Plan.Carrier` names the insurer; each claim carries a rendering provider identified by a 10-digit NPI. |
| MBI | The member's Medicare ID: the 11-character code printed on the Medicare card, like `1EG4-TE5-MK73`. Letters that are easy to misread (B, I, L, O, S, Z) are never used. | The `Mbi` value object: 11 alphanumeric characters from the CMS-safe alphabet, position 1 never `0`; dashes optional on input and normalized away, re-inserted only for display. |
| NPI | A provider's 10-digit ID number. The last digit is a checksum computed from the first nine, so a mistyped NPI fails validation instead of paying the wrong doctor. | The `Npi` value object implementing the official Luhn check digit over the constant prefix `80840` plus the first 9 digits; claim intake rejects invalid NPIs up front (`NPI_INVALID`). |
| AEP / ICEP / SEP | The windows when a member may enroll. AEP is the annual open window (October 15 to December 7, for coverage starting January 1). ICEP is the first-time window around the start of Part B (the three months on either side). A SEP is a special window triggered by a life event (a move, losing other coverage, and similar), with coverage starting the first of the next month. | `EnrollmentRules.Validate`: `IsWithinAep`, ICEP as ±3 months around `PartBEffective`, and `SepReason` (Moved, LostCreditableCoverage, DualEligible, LowIncomeSubsidy, FiveStar) with first-of-next-month effective dates. A five-star plan accepts a switch any month of the year. |
| Adjudication | Deciding a claim: check it was filed on time, that the member was covered that day, and that it is not a duplicate; then price every line (what the plan pays, what the member owes). | `AdjudicationEngine` runs ordered claim rules (CO-29 timeliness, CO-27 coverage, CO-18 duplicate; first denial wins), then `BenefitCalculator` prices each line: fee allowance, deductible, coinsurance, out-of-pocket cap, all in integer cents. |
| CO vs PR codes | Every unpaid dollar on a claim carries a code saying who absorbs it. CO (Contractual Obligation) means the provider must write it off: the plan's decision is final. PR (Patient Responsibility) means the member owes it: deductible, coinsurance, copay. The examples this repo denies with: CO-29 (filed too late), CO-27 (no coverage on the service date), CO-18 (exact duplicate of an earlier claim). | The `DenialCode` enum plus canonical descriptions. CO-18/27/29 are claim-level: they deny the whole claim and every line inherits the code. CO-96 (non-covered service) and PR-1/2/3 are line-level, so a claim can pay overall while one line is CO-96 and another carries PR-2. |
| Benefit accumulators | The member's running totals for the year: how much of the deductible is already met, and how much of the out-of-pocket cap. Once the cap is reached, the plan pays everything for the rest of the year. | `BenefitAccumulator`, tracked per member per benefit year (not per plan): deductible met and OOP met. Advanced line by line by the calculator, upserted by the commit procedure, and shown as YTD figures in member 360. |
| EOB | Explanation of Benefits: the statement that shows how a claim was decided, line by line: what was billed, what was allowed, what the plan paid, what the member owes, and the code for every reduction. In MediFlow, the claim detail page is the EOB. | The claim detail view: header totals, line-level remittance with adjustment codes, and the audit timeline; the MCP `get_claim` tool returns the same shape as text. |

## Engineering terms (the build side)

| Term | In plain English | Precisely |
|---|---|---|
| Transactional outbox | Saving a claim and its work ticket in one database write, so work can never be lost in the gap between "claim saved" and "queued for processing". | An `OutboxMessage` row committed inside the intake EF Core transaction; the worker polls pending messages. Exactly-once processing intent over at-least-once delivery ([ADR 0005](adr/0005-transactional-outbox-leasing.md)). |
| Leasing | A worker checks out a claim for a fixed time, like a library book. If the worker crashes, the checkout expires and another worker can take the claim; only the current holder can file the result. | `usp_LeaseNextClaims` stamps a `LeaseToken` and a 2-minute `LeasedUntilUtc` using `READPAST`/`UPDLOCK`; the commit procedure rejects results with the wrong token (`THROW 51002`); five attempts dead-letter. |
| TVP (table-valued parameter) | A way to send a whole table of rows to the database in one call, like passing a spreadsheet instead of reading values out one row at a time. | `dbo.AdjudicationLineResultType`: all line outcomes of a decision travel to `usp_RecordAdjudicationResult` as one typed parameter, committed in a single transaction ([ADR 0006](adr/0006-tvp-atomic-commit.md)). |
| Row lock | The database's "one clerk at the counter" rule: two workers reaching for the same claim line up instead of both winning. | The `READPAST`/`UPDLOCK` hints in the leasing procedure serialize leasing of the same outbox rows without blocking workers leasing different rows. |
| Dead letter | The shelf for work that failed too many times. A claim that fails adjudication five times stops for operator review instead of silently disappearing; it is visible on the operations page and can be put back in the queue. | `ClaimStatus.DeadLettered` after five attempts (or the sweep for claims orphaned by crashed workers); requeued via `POST /api/v1/claims/{id}/adjudicate`, which drops a new, immediately available outbox message. |
| Stored procedure | A named program stored inside the database itself. MediFlow keeps its heaviest queries and its claim-commit logic there, so the database enforces the rules rather than each caller hoping to. | Eight `CREATE OR ALTER` procedures applied as embedded resources by `SqlScriptRunner` on boot, after migrations; invoked through Dapper for reads and raw ADO.NET for the TVP commit. |
| MCP | A standard way for an AI assistant to call a program's tools. MediFlow's MCP server answers operational questions from chat; it can look but not touch. | Model Context Protocol server over stdio (C# SDK) exposing eight read-only tools over the same reads and domain rules the dashboard uses; adjudication appears only as a dry-run preview that writes nothing ([mcp-server.md](mcp-server.md)). |
| Testcontainers | A testing technique that runs the real database in a throwaway container, so SQL behavior is tested against actual SQL Server rather than a stand-in. | One SQL Server container per test assembly in `TestDatabaseFixture` (azure-sql-edge on arm64 laptops, mssql 2022 on CI), migrated, proc-loaded, and seeded like production bootstrap. |
